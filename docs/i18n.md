# Internationalisation & multi-currency

Zero-dependency i18n for any country. The list of UI languages lives in one
registry, `src/lib/i18n/languages.ts`; today: **en (US), en-GB, de, de-CH, fr,
fr-CH, it, it-CH** (complete) and **es** (beta), with nl, pt, pt-BR, pl, sv,
da and ar planned. Currencies: **CHF, EUR, USD, GBP** (any ISO 4217 code Intl
knows also works). Adding a language: [`docs/i18n/ADDING_A_LANGUAGE.md`](i18n/ADDING_A_LANGUAGE.md).

## Why no library

Typed JSON dictionaries + a ~150-line ICU-lite formatter cover what we need
(interpolation, plurals, select) with compile-time key checking and no bundle
cost. `next-intl` would add routing/middleware we don't need (locale is a user
and tenant setting, not a URL segment). Revisit if we need ICU number/date
skeletons inside messages or URL-prefixed marketing pages.

## Catalogs and regional variants

- `src/messages/en.json` is the source (US English). Base catalogs: `de.json`
  (standard German, with "ß"), `fr.json`, `it.json`, `es.json`.
- Regional variants are thin **overlays**, merged `en <- base <- overlay`, so a
  missing key always resolves:
  - `de-CH` (generated): every "ß" becomes "ss" + Swiss terms from
    `src/messages/overlays/de-CH.terms.json` (Total, Anlass, Traktanden,
    Spital, Znüni …).
  - `en-GB` (generated): British spelling (programme, colour, cancelled,
    instalment …) + `overlays/en-GB.terms.json` (Autumn, postcode).
  - `fr-CH`, `it-CH` (hand-written): NPA, dîner/souper, posteggio …
- `npm run i18n:sync` regenerates the generated overlays and
  `src/messages/index.ts` (the catalog index); the checker fails when they are
  out of date.

A tenant enables **languages** (de, fr, it, en) and picks a **region per
language** (default: its country). The region selects the regional catalog
(`de` + CH → de-CH, `en` + CH → en-GB) and the Intl formats (`en` + CH →
`en-CH`: CHF 1'234.50, 21.03.2026). Stored in `organizations.default_locale /
supported_locales`, mirrored in `app_settings.default_locale /
enabled_locales / settings.languages`, regions in
`app_settings.settings.localization.regions`. Admin UI: Settings → Languages.

## Locale resolution

`user preference → locale cookie → Accept-Language → tenant default → en`

- **User preference** — `profiles.locale`, counted only when
  `profiles.locale_set_at` is set (the column defaults to `'en'` for everyone).
- **Cookie** — `locale`, written by the language switcher (works signed out).
- **Accept-Language** — best match through the registry fallback chains
  (`de-CH,de;q=0.9,en;q=0.8` → de-CH, or de when the club offers "de").
- **Tenant default** — `app_settings.default_locale`.
- Every step is constrained to the tenant's enabled languages.

`<html lang dir>` come from the resolved regional catalog and the registry.
Emails, notifications and PDFs use the **recipient's** language (profile
choice, or the language they used on the page), with the club's formats.

## RTL

The registry carries `dir`; unknown tags resolve by language/script
(`directionOf`). Layout code uses logical utilities (`ms-/me-/ps-/pe-`,
`start-/end-`, `border-s/e`, `text-start/end`) and `rtl:` variants where an
animation or gradient has a side. No RTL catalog ships yet; `ar` is planned.

## Usage

```tsx
// Server component / action
import { getI18n } from "@/lib/i18n/server";
const { t, f } = await getI18n();
t("invoices.due", { date: f.date(inv.dueDate) });
f.money(inv.total);                         // tenant currency
t.dynamic(`status.${row.status}`, undefined, row.status); // runtime keys

// Client component
import { useT, useFormat } from "@/lib/i18n/client";
const t = useT(); const f = useFormat();

// Emails / PDFs / cron (no request)
import { getStandaloneI18n } from "@/lib/i18n/messages";
const { t, f } = getStandaloneI18n({ locale: profile.locale, country: org.country, currency: org.currency });

// Primitives
import { formatMoney, formatDate, firstDayOfWeek, dateOrder } from "@/lib/format";
formatMoney(1234.5, "CHF", "de-CH"); // CHF 1'234.50
formatMoney(1234.5, "EUR", "de-DE"); // 1.234,50 €
formatMoney(1234.5, "USD", "en-US"); // $1,234.50
```

Messages: `"{count, plural, =0 {No invoices} one {# invoice} other {# invoices}}"`.

## Adding / changing strings

1. Add the key to `src/messages/en.json` (source, US English).
2. Add it to every **complete** base catalog (`de`, `fr`, `it`) — `tsc` fails
   until all have it. Beta catalogs (`es`) may lag; they fall back to English.
3. German base is standard German (ß allowed); never edit `de-CH.json` or
   `en-GB.json` by hand — Swiss/British wording goes into
   `src/messages/overlays/<tag>.terms.json`, then `npm run i18n:sync`.
4. `npm run i18n:check -- --strict` (missing/extra keys per status, placeholder
   parity, plural `other` branches, no "ß" in de-CH, overlays in sync, unknown
   `t("…")` keys in `src/`, strings identical to English).
5. `npm run i18n:coverage` shows % translated per language.

## Status

Converted: app shell + navigation + notification bell, login, public
registration flow, parent home/invoices, language switcher in all shells,
Settings → Languages, parent account language, transactional email templates,
notification templates, invoice / ops-invoice PDF (incl. the QR-bill payment
part labels), donation receipts, member cards.

Not yet converted (hard-coded English still present): several admin settings
pages (club profile, branding, billing, privacy forms), parent account page
headings. Invoice language on a single invoice (`invoices.locale`) is still
limited to the five base languages by the money RPCs.
